# Phase 2.1 — Capture corrections

**Branch:** `feature/bitbus-capture-fixes`
**Commit:** `43fc062` — `fix(operations): complete phase 2.1 capture corrections`
**Status:** ✅ Verification gate passed. Committed. Awaiting owner `approved phase 2.1`.

## 1. Done

- Centralized the two-tier policy in `ReadingApprovalPolicy`. Generator, routine tank-level, and feeder lines are saved as `Recorded`; DailyClosing meter readings and receipt/transfer tank events are `Pending`. The policy also provides the common `IsOfficial` predicate. Recorded Tier-1 generator, tank, and feeder lines can be voided with a mandatory reason and audit fields.
- Added tank event structure: parent-main-tank and generator links, filtered single-active daily tank per generator, receipt/transfer event types, linked transfer sides, before-level and delivery-note fields, and validation of required before/after photos.
- Added browser-canvas photo stamping with capture time and equipment code before JPEG/WebP compression, plus focused unit coverage.
- Preserved multi-line photo references and reports a reuse warning when an attachment was already linked to another capture entity.
- Normalized capture time to the minute, added a submission-level time default, line overrides, selectable DailyClosing business date, device-sent time and skew metadata.
- Added device line UUIDs, per-line `accepted`, `duplicate`, `duplicate_time`, and `rejected` results, a 50-line batch limit, and `AwaitingPhoto` for data-first offline submissions. Invalid independent lines are rejected without discarding valid lines; a repeated reading in the same minute is detected both within a request and against persisted data.
- Kept the vertical-cylinder/conical-bottom geometry behind `ITankGeometryStrategy`, added calibration preview API, required geometry fixtures, and optional generator peak-load / air-pressure fields.
- Replaced the active Bitbus visual shell’s visible logo/favicons/page title and removed external Google-font loading. Existing dark/light toggle and coloured navigation icons remain available.
- Made PostgreSQL the configured FuelTrack runtime/design-time provider. Added a trusted PostgreSQL tenant-schema upgrade (`002_bitbus_operational_capture.sql`) and catalog for the Phase 1/2/2.1 tables; new tenant provisioning applies it inside the same Platform transaction as baseline provisioning.

## 2. Not done (and why)

- A Platform operation that enumerates and upgrades **existing** tenant databases has not been added. `TenantSchemaUpgradeCatalog` defines the trusted v2 upgrade and `TenantSchemaMigrator` can execute it atomically per tenant, but the Platform has no approved admin orchestration command/job to invoke it for existing tenants. This must be chosen and run deliberately; tenant databases must not be bulk-updated implicitly.
- The brief requires a self-hosted font. No approved local font file or font licence was supplied, and adding a font package/CDN would violate the no-new-dependencies rule. The application therefore uses its existing system-font fallback after removal of the external Google request.
- No build, automated test, EF command, restore, package installation, migration execution, reset, or browser build was run in this environment, by owner instruction.

## 3. Decisions applied

- PostgreSQL is the only intended Bitbus runtime database. Historical migrations were not edited. The tenant route uses versioned, transactionally applied PostgreSQL SQL; the legacy EF migration chain must not be assumed portable to an existing non-tenant SQL Server database.
- Tenant idempotency remains scoped to `(TenantId, UserId, ClientRequestId)`; `Guid.Empty` is the single-tenant scope.
- Tier-1 approval escalation is station-configurable through `Tier1RequiresApproval`, defaulting to the v4 workflow (no review).
- The validated tank shape is vertical cylinder with a conical bottom. Peak load and air pressure are optional.

## 6. Migrations / schema

- New PostgreSQL tenant schema upgrade: `MultiTenancy/002_bitbus_operational_capture.sql` (additive `CREATE ... IF NOT EXISTS` / `ALTER ... ADD COLUMN IF NOT EXISTS` and PostgreSQL partial indexes).
- EF model changes cover the Phase 2.1 columns, relationships, statuses and indexes. No historical migration was edited, no database was migrated, and no destructive operation was performed.

For a **new** Platform tenant, `TenantProvisioningService` opens the tenant PostgreSQL connection, starts a transaction, creates the baseline schema, runs the v2 catalog SQL, records schema version 2, seeds the tenant, and commits. `MigrationRunner` remains the legacy/default EF path; it is not the tenant fan-out mechanism.
