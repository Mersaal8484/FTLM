# خطة PostgreSQL وتعدد المستأجرين وإدارة الاشتراكات

**الحالة:** قيد التنفيذ على فرع `development`.
**تاريخ الإنشاء:** 2026-11-02

## 1. الهدف والنطاق

تحويل FuelTrack إلى نظام يمكن تشغيله لعدة عملاء مستقلين على PostgreSQL، مع مخطط قاعدة بيانات مستقل لكل مستأجر. تُبنى واجهة إدارة المنصة والمستأجرين والاشتراكات باستخدام ASP.NET Core، وتبقى React واجهة عمليات العملاء اليومية. تبقى خدمات API المشتركة في ASP.NET Core مع فرض صلاحيات المستأجر والمستخدم على الخادم. أكّد المستخدم أن النظام الجديد يبدأ بقاعدة PostgreSQL جديدة ولا توجد بيانات SQL Server فعلية يلزم نقلها.

يشمل العمل التصميم والتنفيذ والترحيل والاختبارات والتشغيل والوثائق. لا يتضمن هذا المستند موافقة على تغيير بيانات إنتاج أو تشغيل ترحيل فعلي؛ تُجهز خطة التحويل والتحقق قبل تحديد نافذة الانتقال.

## 2. الوضع الحالي الذي يؤثر على الخطة

- `src/FuelTrack.Infrastructure/DependencyInjection.cs`: سياق واحد يختار SQL Server أو SQLite؛ توجد إدارة مستخدمين وأدوار عبر ASP.NET Core Identity.
- `src/FuelTrack.API/Program.cs`: مصادقة JWT وSignalR، وتهيئة قاعدة البيانات والبيانات الأولية عند البدء. تنفذ التهيئة حالياً على قاعدة واحدة.
- `src/FuelTrack.Infrastructure/Migrations/`: سلسلة طويلة من ترحيلات EF Core خاصة بـ SQL Server؛ لا يمكن افتراض أن إعادة تشغيلها على PostgreSQL كافية.
- Hangfire مرتبط بـ SQL Server، وتوجد مهام صيانة ونسخ احتياطي واستعلامات تعتمد على SQL Server وتحتاج مراجعة وتحويلاً.
- `docker-compose.yml` يشغّل SQL Server؛ وواجهة React تضم حالياً إدارة المستخدمين والأدوار التي يلزم تحديد مصيرها في التصميم الجديد.
- النطاق الحالي للمستخدمين داخل الفروع والمحطات (`UserScope`) صلاحية داخل المستأجر؛ لا يغني عن عزل المستأجرين.

## 3. البنية المقترحة

```text
مسؤول المنصة ── ASP.NET Core Admin (Razor Pages) ── خدمات إدارة المنصة
                                                       │
عملاء المستأجر ── React ── ASP.NET Core API ── تحديد المستأجر والتحقق من الاشتراك
                                                       │
                                         PostgreSQL: قاعدة بيانات واحدة مبدئياً
                                           platform: بيانات المنصة والاشتراكات
                                           tenant_<id>: بيانات المستأجر ومستخدميه
                                           tenant_<id>: بيانات مستأجر آخر
```

1. **المنصة:** مخطط `platform` للمستأجرين والنطاقات والباقات والاشتراكات والفواتير وسجل نشاط مسؤولي المنصة وحالة تجهيز المستأجر وإصدار مخططه. أسماء المخططات تولّد داخلياً من معرّف ثابت؛ لا تُقبل كمدخل مباشر من الطلب.
2. **المستأجر:** مخطط خاص يحتوي بيانات التشغيل ومستخدمي المستأجر وأدوارهم وصلاحياتهم ونطاقاتهم وسجل التدقيق الخاص بهم. صلاحية الفروع والمحطات تعمل داخل هذا المخطط.
3. **حسابات المنصة:** هوية منفصلة لمسؤولي المنصة، لا تُمنح تلقائياً صلاحيات مستخدم مستأجر. دخول الدعم إلى بيانات مستأجر يتطلب سياسة صريحة وسجلاً تدقيقياً.
4. **العناوين:** نطاق فرعي لكل مستأجر حسب اختيار المستخدم، مع اقتراح نطاق منفصل للإدارة. يُحدد المستأجر من مضيف موثوق مسجل في المنصة، وتُرفض النطاقات غير المعروفة. يُربط التوكن والجلسة والطلب بنفس معرّف المستأجر بعد التحقق؛ لا يُوثق بمعرّف يرسله العميل وحده.
5. **العزل:** `search_path` وحده ليس حدّاً أمنياً إذا كان حساب قاعدة البيانات يستطيع الوصول إلى جميع المخططات. يجب إثبات استخدام صلاحيات قاعدة بيانات مقيدة لكل مستأجر أو بديل مكافئ قابل للتدقيق، وفصل صلاحيات إنشاء المخططات والترحيل عن حساب التشغيل. تضبط الاتصالات المجمّعة بحيث لا يتسرب سياق المستأجر؛ لا يضاف `public` قابل للكتابة إلى مسار البحث الموثوق.
6. **واجهة الإدارة:** اقتراح مشروع `src/FuelTrack.Admin` بـ Razor Pages وASP.NET Core Identity/الكوكيز لإدارة المنصة. تُدار حسابات المستأجرين وأدوارهم من واجهات ASP.NET Core حسب اختيار المستخدم؛ تظل React للعمليات اليومية والتقارير.
7. **الخدمات المشتركة:** أسماء الكاش، قنوات SignalR، الملفات، سجلات التدقيق، حدود المعدل، والمهام الخلفية تتضمن هوية المستأجر الموثقة. تُفحص الصلاحيات عند الاتصال وبث الرسائل والعمل غير المتزامن.

**قيد تقني يجب حسمه مبكراً:** توثيق Microsoft يذكر أن نموذج مخطط لكل مستأجر غير مدعوم مباشرة في EF Core، خصوصاً مع إدارة الترحيلات. لذا يلزم نموذج تجريبي واختبارات انتقال وتزامن قبل اعتماد تنفيذ مُعين، لا الاكتفاء بتغيير `HasDefaultSchema`. كما أن نموذج EF المخزن مؤقتاً وتاريخ الترحيلات وعزل الاتصالات يجب اختبارها وفق الاستراتيجية المختارة. راجع [Microsoft: تعدد المستأجرين في EF Core](https://learn.microsoft.com/en-us/ef/core/miscellaneous/multitenancy) و[PostgreSQL: المخططات والصلاحيات](https://www.postgresql.org/docs/current/ddl-schemas.html).

## 4. نموذج الاشتراكات المقترح

- كيانات أولية: `Tenant`, `TenantDomain`, `Plan`, `PlanFeature`, `Subscription`, `Invoice`, `PaymentRecord`, `PlatformAuditLog` وعمليات تجهيز المستأجر وترحيله.
- حالات دورة حياة المستأجر: قيد الإنشاء، فعّال، موقوف، مؤرشف؛ لا يُفعّل قبل اكتمال إنشاء المخطط والبيانات الأولية.
- حالات الاشتراك: تجريبي، فعّال، فترة سماح، موقوف، منتهٍ. تواريخ البداية والنهاية والمنطقة الزمنية وقواعد التجديد وتاريخ تغيير الباقات تكون واضحة وقابلة للتدقيق.
- الباقة تحدد الوحدات المسموحة والحدود المتفق عليها مثل المستخدمين أو المحطات. يفحص الخادم الميزات والحدود عند كل عملية مؤثرة، وليس إخفاء الشاشة فقط. تُعرّف استجابة موحدة عند انتهاء الاشتراك أو رفض الميزة.
- اقتراح المرحلة الأولى: اشتراكات وفواتير ومدفوعات تُسجل يدوياً، من دون تخزين بيانات بطاقات. أي بوابة دفع وتفاصيل الضرائب والعملات والفواتير مؤجلة لقرار المنتج؛ لا يُفترض إجراء خصم أو دفع آلي.
- يحدد المنتج قبل التنفيذ أثر انتهاء الاشتراك على القراءة والكتابة والتصدير، ومدة السماح، وسياسة إيقاف المستأجر واستعادته.

- [ ] اختبار إنشاء المخطط وتحديثه وإعادة المحاولة بعد الفشل، وتاريخ ترحيلات مستقل ومزامنة متوازية بقفل مناسب.

- [ ] قياس أثر عدد المخططات وحجم الذاكرة والاتصالات؛ توثيق حدود التصميم وآلية التوسع والبديل إذا فشل الإثبات.

**القبول:** اختبارات PostgreSQL حقيقية ناجحة وتقارير توضح كيف يُطبّق ويُحدّث ويُعزل كل مخطط. عند فشل إثبات الأمان أو الترحيل لا تبدأ مراحل الاعتماد على التصميم حتى تصحيح البديل.

**التقدم 2026-11-03:** أُضيف نموذج مستقل في `tests/TenantIsolation.Proof` يعمل على PostgreSQL مؤقت؛ نجحت اختبارات صلاحيات دور منفصل لكل مستأجر، واستعلامات EF المتزامنة، وتجميع الاتصالات، وترقيات SQL التجريبية المتزامنة والتراجع بعد فشلها. أضيفت قواعد توليد أسماء المخططات وتطبيع أسماء النطاقات. هذا إثبات محدود لجداول تجريبية، وليس دليلاً على عزل تطبيق FuelTrack أو ترحيلات EF أو الهوية أو SignalR والمهام؛ تبقى معايير المرحلة مفتوحة.

أُضيف مشروع `src/FuelTrack.Platform` وسياق أولي وترحيل EF لمخطط المنصة وسجل مستأجر بنطاق فريد، واختُبرا على قاعدة PostgreSQL مؤقتة؛ لا يزال مشروع API العملاء غير مرتبط بهما، ولا ينشئان مخططات المستأجرين. يلزم استكمال ترحيلات المنصة وأدواتها واستراتيجية مخططات المستأجرين قبل استخدامهما في تشغيل فعلي.

**تحديث:** أُضيفت لوحة `src/FuelTrack.Admin` أولية تتصل بمخطط المنصة على PostgreSQL، مع تسجيل الدخول وتسجيل مستأجر بحالة التجهيز وإضافة باقة واشتراك يدوي ومنع تداخل اشتراكات المستأجر. تعمل محلياً عبر `docker-compose.platform.yml` بصورة تطويرية مستقلة. لا تُفعّل المستأجرين ولا تفرض الاشتراك على API، ولا تتضمن بعد إدارة مستخدمي المستأجر أو الفواتير وسجل التدقيق؛ لا تعدّ نظاماً متعدد المستأجرين جاهزاً. لا يزال API العملاء يعمل على SQL Server.

**تقدم إضافي:** أُضيف مزود Npgsql وصيغ فهارس مناسبة لـ PostgreSQL إلى نموذج EF الحالي، وخدمة تجريبية لإنشاء مخطط كامل ودور مقيد للمستأجر داخل معاملة واحدة. نجح `tests/PostgresModel.Proof` في إنشاء نموذج FuelTrack الكامل في مخططين على PostgreSQL، وعزل مستخدمي Identity والفروع، ورفض الوصول المتبادل وقراءة سجل إصدار المخطط، ورفض الإنشاء المكرر. اختُبر أيضاً بقاء صيغة فهارس SQL Server. أُضيف فحص لنطاق المستأجر وحالته واشتراكه ومطابقة معرفه مع المطالبة؛ لم يُربط بعد بمصادقة API.

خدمة تجهيز المخطط ما زالت **تجريبية وغير مرتبطة بلوحة الإدارة**. ثُبت نص الإنشاء الأولي كملف SQL مضمّن مستقل عن تغييرات نموذج EF اللاحقة. لا يثبت الاختبار الحالي سلامة جميع التقارير والمهام وSignalR أو تأمين API في نمط المستأجرين.

**تحديث تنفيذي:** أُضيف سجل مشفّر لاعتماد قاعدة كل مستأجر باستخدام AES-GCM، مع واجهة لمصدر مفاتيح خارجي ومزود ملفات أسرار مقيد الصلاحيات على Linux. أُضيفت إجراءات تجريبية لتدوير كلمة المرور وإعادة تشفير الاعتماد بمفتاح جديد، وكذلك محرك ترقيات SQL موثوقة يستخدم قفل PostgreSQL وبصمات للترقيات. اختبارات PostgreSQL غطت العزل، وتغيير كلمة المرور والمفتاح، وفشل العملية والتراجع، وترقيات متزامنة وفاشلة. لم يُربط مصدر مفاتيح الإنتاج بعد، ولا توجد آلية لتنسيق إنهاء الاتصالات القديمة بين النسخ. يتطلب نشر الميزة أيضاً حماية سجلات PostgreSQL؛ لا يرسل الكود كلمة المرور الصريحة في SQL، لكن قد تظهر قيمة SCRAM المحسوبة في السجل.

**تحديث لاحق:** أُضيف إلى لوحة الإدارة مسار تجهيز اختياري ينشئ المخطط ودور PostgreSQL والاعتماد المشفّر في معاملة واحدة، دون تفعيل المستأجر. يُتاح فقط بعد إعداد مصدر مفتاح خارجي، ويمكن إضافة `docker-compose.platform.provisioning.yml` لتركيب مجلد أسرار للقراءة فقط. نجحت تجربة الإعادة والتحقق من التراجع بعد فشل حفظ الاعتماد. فُعّل زر التجهيز في بيئة التطوير المحلية بمفتاح محفوظ في وحدة Docker مخصصة؛ لم يُختبر نشره للإنتاج.

اختُبر مسار اللوحة نفسه في `tests/AdminProvision.Proof` باستخدام قاعدة ومفتاح مؤقتين: تسجيل الدخول، إنشاء مستأجر، تجهيز مخططه وإعادة الطلب، مع بقائه غير مفعّل. وأثبت اختبار PostgreSQL منفصل تراجع المخطط والدور والاعتماد عند الفشل، ورفض توكن موقّع لمستأجر على نطاق مستأجر آخر مسجّل.

أُضيف مسار تجريبي لسياق الطلب: النطاق المسجل والاشتراك الفعال ومطالبة `tenant_id` الموقّعة تحدد اتصالاً بدور المستأجر، ويُضاف المعرّف إلى توكنات الدخول وSignalR. اختُبر تسجيل دخول Identity حقيقي ورفض التوكن الصحيح على نطاق مستأجر آخر، لكن ما زال تشغيل API متعدد المستأجرين مرفوضاً صراحةً إلى حين دمج واختبار نطاق البث والكاش والمهام و2FA ومصدر المفاتيح معاً. لا تزال سياسة تدوير الاتصالات الحية وتسجيل SCRAM وتكوين الوكيل الموثوق والمصادقة في الإنتاج غير مكتملة.

أُصلح نطاق التقارير للمستخدم بلا صلاحيات، ومطابقة نطاق مستقبلي الإشعارات، وفحص نطاقات الانضمام إلى مجموعات SignalR. أُضيفت مجموعات بث ومفاتيح كاش مرتبطة بسياق المستأجر، ومشغّل أرشفة يستخدم اتصال المستأجر واشتراكه وقفل PostgreSQL. اختُبر العزل باستخدام اختبارات وحدات للبث والكاش واختبار PostgreSQL للأرشفة؛ إبطال الكاش الموزع بين نسخ الخدمة وجدولة جميع المهام لم يكتمل. تفعيل `MultiTenancy:Enabled` في API مرفوض صراحةً حتى اكتمال الربط الآمن.

**اختبار SignalR إضافي:** شُغّل Hub فعلي في Kestrel مع اتصالَي WebSocket وهوية موقّعة لمستأجرين، واختُبر عزل البث العام والرسائل الموجهة للمستخدم والمجموعة، ورفض هوية مستأجر لا تطابق السياق. كشف الاختبار أن SignalR ينشئ نطاق خدمات منفصلاً عن نطاق طلب الاتصال؛ أُصلح Hub لاستخدام سياق وخدمات طلب الاتصال عند فحص المستأجر والصلاحيات. الاختبار يستخدم تحديد مستأجر تجريبياً داخل خادم الاختبار، ولا يثبت تكامل API الكامل أو التشغيل عبر نسخ متعددة، لذلك يبقى التفعيل محظوراً.

**اختبار API الفعلي:** شُغّل API بعملية منفصلة على loopback في وضع اختبار حصري لقاعدة مؤقتة اسمها `model_proof`؛ نجحت اختبارات دخول مدير تجريبي، وإنشاء فرع ومحطة وتسجيل التدقيق في مخطط المستأجر، ورفض تسجيل مجهول، ونقل التوكن إلى نطاق مستأجر آخر، والدخول بعد انتهاء الاشتراك. أُصلح نقل سياق المستأجر إلى نطاق تدقيق مستقل، وأُزيلت سلسلة الاستعلام من سجل الطلبات لتجنب تسجيل توكنات SignalR. لا يغطي الاختبار جميع العمليات والمهام أو بيئة النشر؛ وضع اختبار API ليس صالحاً لتشغيل العملاء، ولا يزال وصولهم محظوراً.

تطلب شاشة التجهيز بريد مدير المستأجر وكلمة مروره؛ يُنشأ حساب Identity ودور Admin ونطاقه وصلاحياته ضمن معاملة التجهيز، مع بقاء المستأجر غير مفعّل. اختُبر التجهيز وإعادة المحاولة من لوحة الإدارة على قاعدة مؤقتة. أُصلح تدفق المصادقة الثنائية بكلمة مرور ثم تحدٍّ محدود الصلاحية يُستهلك مرة واحدة قبل إصدار التوكن، واختُبرت حالات الرمز الصحيح والخاطئ والتحدي المكرر وعبر المستأجرين على PostgreSQL، واختُبرت واجهة إدخال الرمز. لا يزال يلزم منع إعادة استخدام رمز TOTP نفسه عبر تحديات مختلفة، وتطبيق واختبار رموز الاسترداد وحماية أسرار المصادقة الثنائية، واختبار التدفق كاملاً عبر HTTP قبل تفعيل الوصول. لم تُفعّل خدمة العملاء متعددة المستأجرين.

### المرحلة 2 — منصة PostgreSQL والبيئة

- [ ] إضافة Npgsql وتكوين PostgreSQL وتصميم سياق المنصة وسياق المستأجر والترحيلات الخاصة بكل منهما، مع إبقاء SQL Server متاحاً أثناء التحويل فقط.
- [ ] إعداد حاوية PostgreSQL وتخزين دائم وفحوص الجاهزية، ومستخدمين منفصلين للتشغيل والترحيل؛ توثيق الأسرار والاتصال الآمن.
- [ ] إنشاء ترحيل PostgreSQL ابتدائي من النموذج المعتمد بدلاً من تشغيل ترحيلات SQL Server كما هي، ومراجعة اختلاف الهوية والتواريخ و`decimal` وJSON والحروف والفهارس والقيود.
- [ ] تحويل SQL الخاص بـ SQL Server، إجراءات القفل والصيانة والإحصاءات، والفهارس والنسخ الاحتياطي. اعتماد بديل PostgreSQL ملائم ومختبر لـ Hangfire أو بديل وظائف واضح؛ لا تغيير أو مسح جدول مهام قائم دون خطة.
- [ ] إزالة الاعتماد على تهيئة مستأجر واحد تلقائياً عند بدء API، ونقل تجهيز المخططات والترحيلات إلى عملية مؤمنة قابلة للتكرار.

**القبول:** تشغيل نظيف على PostgreSQL من الصفر، وإنشاء مخططين وترقيتهما، وفحوص صحة ونسخ واستعادة مثبتة.

### المرحلة 3 — هوية المستأجر والأمن

- [ ] تنفيذ `TenantResolver` وسياق مستأجر محدد العمر، وربطه بالنطاق المسجل وباشتراك المستأجر وبهوية المستخدم قبل الوصول للبيانات.
- [ ] فصل سياسات حسابات المنصة وحسابات المستأجر وتسجيل الدخول والتوكنات والكوكيز، مع اختبار CSRF وCORS وSignalR وتسجيل الخروج وتجديد الجلسات.
- [ ] ربط مهام Hangfire والخدمات الخلفية وModbus والتقارير والتصدير والتخزين والكاش بمعرّف مستأجر موثوق؛ منع التسرب في السجلات والمخرجات.
- [ ] المحافظة على الصلاحيات والأدوار و`UserScope` لكل مستأجر، واختبار جميع مسارات القراءة والكتابة وعزل الأخطاء.

**القبول:** اختبارات عزل سلبية وتزامن ناجحة تشمل API وSignalR والمهام والملفات والكاش؛ لا يستطيع مستخدم مستأجر الدخول إلى بيانات مستأجر آخر.

### المرحلة 4 — لوحة المنصة واشتراكاتها

- [ ] إنشاء لوحة ASP.NET Core بواجهات عربية وإنجليزية، مصادقة منفصلة، وصلاحيات لمسؤولي المنصة وحماية النماذج وسجل تدقيق.
- [ ] إدارة المستأجرين والنطاقات والتجهيز وإعادة المحاولة والإيقاف والاستعادة؛ إظهار حالة التهيئة وأخطاء التشغيل دون كشف أسرار.
- [ ] إدارة الباقات وميزاتها وحدودها، الاشتراكات وفترة السماح والفواتير والمدفوعات اليدوية وسجل التغييرات وفق القرارات المعتمدة.
- [ ] تنفيذ واجهات إدارة مستخدمي المستأجر وأدواره وصلاحياته في ASP.NET Core، ونقلها من React بعد التحقق من تكافؤ الوظائف.

**القبول:** رحلة إنشاء مستأجر وتعيين مدير وباقة وتسجيل اشتراك وتفعيل وصوله وإيقافه واستعادته تعمل من اللوحة وتُسجل في التدقيق.

### المرحلة 5 — تطبيق العملاء React

- [ ] ربط تسجيل الدخول والنطاق وسياق المستأجر، والتعامل مع انتهاء الاشتراك والميزات والحدود من استجابات API.
- [ ] فصل صفحات إدارة المنصة عن تطبيق العملاء، ونقل صفحات إدارة مستخدمي المستأجر وأدواره، مع المحافظة على العمليات اليومية.
- [ ] التحقق من الصلاحيات والتقارير والإشعارات واللغة والتوافق مع SignalR لكل مستأجر.

**القبول:** مستأجران يستخدمان التطبيق في الوقت نفسه ببيانات وصلاحيات منفصلة، وتعمل العمليات الأساسية دون صلاحيات منصة.

### المرحلة 6 — تهيئة قاعدة جديدة والانتقال

**قرار المستخدم:** البدء بقاعدة PostgreSQL جديدة؛ نقل بيانات SQL Server ليس مطلوباً ضمن نطاق التنفيذ الحالي. تبقى خطوات النقل أدناه مرجعاً مشروطاً فقط إذا تغيّر هذا القرار لاحقاً. لا تُحذف قاعدة SQL Server الحالية أو وحدة تخزين Docker تلقائياً عند تنفيذ الانتقال.

- [ ] عند وجود بيانات يجب الاحتفاظ بها: اختيار نسخة SQL Server المصدر وتحديد المستأجر الهدف، وتصميم تحويل معرّفات وعلاقات المستخدمين والأدوار و`UserScope` والتواريخ والمرفقات وسجلات التدقيق والبيانات التشغيلية.
- [ ] فحص توافق كلمات مرور Identity، ومفاتيح تشفير البيانات، والتوكنات، والتعامل مع الحسابات التي لا يمكن نقلها دون إعادة تعيين آمنة؛ لا تُنسخ مفاتيح سرية في المستودع.
- [ ] بروفة على نسخة منفصلة: نسخ احتياطي واختبار استعادة، نقل، إعادة ضبط sequences، مقارنة أعداد الصفوف والأرصدة والمجاميع والعينات والقيود ووظائف الدخول والتقارير.
- [ ] خطة نافذة تحويل واضحة: وقف الكتابة، لقطة نهائية، إعادة النقل/الفروق، التحقق، تحويل التوجيه، مراقبة، وإعادة التشغيل الآمن. تجربة الاستعادة قبل الانتقال.
- [ ] تحديد نقطة عدم العودة: بعد قبول كتابات جديدة في PostgreSQL لا يكفي إعادة التوجيه إلى SQL Server؛ يلزم منع الكتابة أثناء التحقق أو آلية معتمدة لإعادة مزامنة التغييرات. لا يُحذف المصدر أو النسخ قبل انتهاء فترة الاحتفاظ المتفق عليها.

**القبول الحالي:** تهيئة قاعدة PostgreSQL جديدة ومخطط المنصة والمستأجر الأول، والتحقق من الهوية والبيانات الأولية والأداء وتجربة الاستعادة. إذا طُلب نقل بيانات لاحقاً، تُطبق معايير المطابقة وخطة التراجع أعلاه بعد تحديد المصدر والموعد ونتائج البروفة.

### المرحلة 7 — الجاهزية والتشغيل

- [ ] اختبارات وحدة وتكامل فعلية على PostgreSQL، واختبارات واجهات وعزل واشتراكات وحمل وترقية فاشلة وتكرار التجهيز.
- [ ] فحوص الصحة والتنبيهات، سجلات قابلة للبحث بحسب المستأجر دون بيانات حساسة، ومراقبة عدد الاتصالات وقفل الترحيلات والمهام.
- [ ] نسخ احتياطي واستعادة تشمل قاعدة المنصة وجميع المخططات، وتجربة استعادة مستأجر منفرد دون الكتابة فوق بيانات غيره، وقياس RPO/RTO الفعليين.
- [ ] تحديث README وCompose ووثائق التشغيل والتعامل مع الحوادث وترقية المستأجرين واستعادة النسخ؛ توثيق قضايا الدعم والسعة والقيود.

**القبول:** تقارير اختبار واضحة، تجربة استعادة ناجحة، وإكمال قائمة التشغيل واعتماد الانتقال.
